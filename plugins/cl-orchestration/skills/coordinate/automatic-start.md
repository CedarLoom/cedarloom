# Automatic start

The checks and the probe that pass before an automatic worker starts ([modes.md](modes.md#modes)): checks 1 to 4, the probe of check 5 with its steps, and its pass rule.

Check 2 runs before every start of an automatic worker (its first start, a retry, each follow-up, the probe), the others before the first automatic worker of each project in a run, in this order; for a project bot, once per UTC day in its first catch-up run (`probe: true`, [bot-catch-up.md](bot-catch-up.md)), and a failure there holds for the rest of that UTC day in place of the run. A failure, except the `--check` read of check 2, runs that project supervised for the rest of the run where [orca.md](orca.md#fallback-to-supervised) offers that fallback, else starts nothing there; write it in the handoff's `Mode:` line and name the check or step in the report. A supervised worker has none of the automatic bounds: the report says so for that project, and with Orca names what its workers run under ([orca.md](orca.md#fallback-to-supervised)).

1. `'<claude path>' --version` is v2.1.323 or later; after a failure the fallback starts no Claude Code worker either ([orca.md](orca.md#start-the-run)).
2. `worker-settings.mjs` wrote the worker's settings file right before the start ([Sandbox on](modes.md#sandbox-on)) and exited 0. A hand-made file can keep a placeholder or a wrong path and still load, with its deny rules pointing nowhere. Then, as the last command before Orca starts the worker's session, `node <skill folder>/worker-settings.mjs --check` with the same arguments exits 0: it reads the file as it is then and passes only the exact text the script writes for that worktree, that project and those domains. Claude Code starts with an empty settings file as with none, so without the sandbox and the file-tool bounds. Any other exit starts no worker: it makes the item BLOCKED, and for the probe it fails check 5.
3. `node <skill folder>/start-checks.mjs --project <project path> --worktree <worktree path>` takes checks 3 and 4 (`--config-dir <folder>` for a worker whose Claude Code configuration folder is not `$CLAUDE_CONFIG_DIR` or `~/.claude`). Exit 0 passes what the script reads; mods and managed settings from device management or the server stay your read. 1 fails, `failed` naming each entry, also for an unreadable file. 2 leaves `read` and `unresolved` to you: read the file each command runs and what each entry names; one you cannot judge fails its check. `unresolved` names what the script does not read: a settings or marketplace key not known to run no command, an `Edit`, `MultiEdit`, `Write` or `NotebookEdit` allow rule outside the worktree, a skill, agent or command file whose frontmatter sets `hooks` or `mcpServers` or opens with an indented line, a `skills`, `agents` or `commands` folder in the `.claude` folder of a subfolder of the worktree (it loads when the worker works there; `node_modules` and `.git` are not searched), a plugin in `<config dir>/skills/`, `.claude/skills/` or `plugins/synced/`, `CLAUDE_CODE_PLUGIN_DIRS`, `CLAUDE_CODE_PLUGIN_CACHE_DIR`; a `--plugin-dir` plugin stays your read. Check 3: no hook, MCP or LSP server, monitor, command setting (status line, `apiKeyHelper` and the like) or `env` of check 4's settings files, `managed-mcp.json`, `.claude.json`, either checkout's `.mcp.json` or an enabled plugin, and no process an enabled mod starts, runs a file inside the repository or a tool that loads the repository's code or configuration (a formatter, a linter, a package script): these run outside the sandbox, so a worker that edits such a file gets its code run unsandboxed. The script fails a command that names the repository, a relative path or `CLAUDE_PROJECT_DIR`, or runs a known such tool, and lists the others in `read`, with each hook that is no command hook.
4. No entry that defeats a bound, in managed settings, the user settings, or either checkout's `.claude/settings.json` or `.claude/settings.local.json`: a `sandbox.excludedCommands` entry (an excluded command runs outside the sandbox, and an allow rule lets it run without a prompt), a `sandbox.network.allowUnixSockets` or `allowAllUnixSockets` entry (the SSH agent, a container socket), an `allowRead`, `allowWrite` or `additionalDirectories` entry outside the worktree, a `true` for `sandbox.allowAppleEvents` (a command then runs unsandboxed and can script running apps), `allowNestedUserNamespaces`, `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `network.allowLocalBinding` or `filesystem.disabled` (the template pins each to `false`; whether that wins over the user settings is not tested), a `sandbox.network.allowMachLookup`, `network.httpProxyPort` or `network.socksProxyPort` entry, a `sandbox.enabledPlatforms` entry that leaves out the host's platform, a `sandbox.ripgrep`, `sandbox.bwrapPath` or `sandbox.socatPath` override, and no GitHub host (`github.com`, a subdomain of it, `*.githubusercontent.com`) in the merged network allow list or in a `WebFetch(domain:...)` allow rule of those files (such a rule may add its host to the sandbox's allow list). Name in the run report the other allow rules and `sandbox.network.allowedDomains` entries of those files: `allowRules` and `allowedDomains`.
5. The probe: one worker with the same launch in a scratch worktree of the project (create `.husky/` there first, and a second scratch worktree of the project beside it before the probe's settings file is written, so that the file names its folder), its spec these steps. Check each result yourself where you can.
   1. Version: as check 1.
   2. The Write and Read tools on a new file in the run folder are refused, and no file appears there. The Write refusal names `blockWritesOutsideWorkingDirectories`, which shows the settings file loaded.
   3. Bash `touch` and `cat` on a file you wrote in the run folder before the probe (its absolute path, filled in) fail with `Operation not permitted`. The file must exist: on macOS the sandbox answers a path that does not exist with `No such file or directory`. On Linux the sandbox mounts an empty tmpfs over a read-denied folder, so there the criterion is that both commands ran on that path (a refusal by a permission rule or a hook fails this step), that `cat` prints none of the file's content, that the worker reports both outputs verbatim, and that you, as the coordinator, then find the file on the host with its content and modification time unchanged.
   4. The Write tool and Bash `touch` on `.claude/settings.json`, `.mcp.json`, `.husky/pre-commit`, `.envrc`, `.npmrc` and `.git` are refused, and Bash `touch` on `<common .git>/hooks/probe`, `<common .git>/config`, `<common .git>/commondir`, `<common .git>/config.worktree`, and `commondir` and `config.worktree` in `<common .git>/worktrees/<id>/` and in the second scratch worktree's folder there (the absolute paths, filled in) fails with `Operation not permitted`. Bash `mv` of the second worktree's folder there to `<its name>.moved` fails and the folder keeps its name. On macOS the message is `Operation not permitted`. On Linux the criterion is the kept name: the folder is a mount point there ([Sandbox on](modes.md#sandbox-on)), so the message may be `Device or resource busy` (`EBUSY`). A touch or the `mv` that passes there shows that the sandbox does not take the rules that name that folder. In the worktree, Bash `printf '' >> .git` exits non-zero with `.git` keeping its content (the shell words the message: zsh `operation not permitted: .git`, bash `.git: Operation not permitted`; on Linux `Read-only file system`; the message may differ), and `mv .git .git.moved` fails with `.git` keeping its name: the template's `sandbox.filesystem.denyWrite` entry closes the file, and the rename also by the sandbox runtime's own rules, on macOS through its move-blocking rules, on Linux through its write deny on a `.git` file.
   5. Bash `<Orca CLI> orchestration run-list --json`, the Orca CLI by its absolute path (on macOS `/Applications/Orca.app/Contents/Resources/bin/orca`, on Linux the path it is installed at), fails with `runtime_unavailable` or `runtime_access_denied`. Any other result, also a command that is not found, fails this step: it tests the bound of [Sandbox on](modes.md#sandbox-on) that keeps the worker from every Orca app.
   6. Bash `curl -sS -I https://example.com` is refused.
   7. Bash `claude -p 'reply ok'` fails, and its output shows a sandbox cause: `Operation not permitted` on a path in the home folder (the program or its configuration; zsh and Node.js word it `operation not permitted`), or a connection the sandbox's proxy refused. The worker reports that output verbatim. A reply, a timeout and any other failure (an expired login, a usage limit, another API error, a refusal by a permission rule or a hook, `command not found`) fail this step, since none shows the sandbox stopped the session. On Linux the tmpfs of step 3 hides the home folder, so the step passes there only on the proxy's refusal, and `command not found` for a program in the home folder fails it. The launch already unsets `CEDARLOOM_ROLE`, and the role guard refuses a command that names it before it runs, so the step leaves the variable out.
   8. A write in the worktree and `git add` succeed; `git push origin HEAD:refs/heads/probe/<r>` is refused, `git -C <W> push origin HEAD:refs/heads/probe/<r>` (a form the deny rule does not match) fails at the network: for an HTTPS origin with `CONNECT tunnel failed, response 403` from the sandbox's proxy, for an SSH origin at its connection (the message may differ). A permission refusal of that call fails this step, since it tests no network bound. Then, as the coordinator, `gitW ls-remote origin refs/heads/probe/<r>` ([Commit and push](commit-and-push.md)) prints nothing; commit on the host as [Commit and push](commit-and-push.md) says, and run its push with `--dry-run`.

Pass rule: every step as stated, and the probe's report arrives as its final answer, read through Orca as [Worker reports](orca-messages.md#worker-reports) says; no report within `stallMinutes` fails it. Steps 2 and 6 also pass on `dontAsk` alone; without the sandbox, step 3 names don't-ask mode instead of `Operation not permitted` and step 8's `git add` is refused. After the probe, first and without git, remove each file that a passing touch of step 4 made in the shared `.git` (an empty `commondir` there stops every git command in the project) and give a folder or `.git` file that a passing `mv` renamed its name back. Then remove both scratch worktrees, each as an automatic worker's: the `commondir` read of [Commit and push](commit-and-push.md) on its folder, then the `worktree remove` command of [Clean up](orca-clean-up.md). `worktree remove` refuses a worktree with changes, untracked or staged: the probe's file when the probe ended before step 8's commit, a file a passing touch of step 4 made in the worktree. For the probe's worktree only, and once you have read those files, add `--force` after `worktree remove`. The second scratch worktree and every worker's worktree are removed without it. Then delete the branch `probe/<r>`: its commit is the probe's, never pushed.
