# Automatic start

The checks and the probe that pass before an automatic worker starts ([modes.md](modes.md#modes)): checks 1 to 4, the probe of check 5 with its steps, and its pass rule.

All five run, in this order, before the first automatic worker of each project in a run; for a project bot, checks 1, 3, 4 and 5 run once per UTC day in its first catch-up run (`probe: true`, [bot-catch-up.md](bot-catch-up.md)), and a failure there holds for the rest of that UTC day in place of the run. Checks 2 to 4 run before every start of an automatic worker (its first start, a retry, each follow-up, the probe), checks 3 and 4 on that worker's worktree: the branch it starts from, or an earlier worker there, can have written settings into it. A failure of check 3 or 4 at a later start, like a failed `--check` read of check 2, makes that item BLOCKED and starts no worker. Any other failure runs that project supervised for the rest of the run where [orca.md](orca.md#fallback-to-supervised) offers that fallback, else starts nothing there; write it in the handoff's `Mode:` line and name the check or step in the report. A supervised worker has none of the automatic bounds: the report says so for that project, and with Orca names what its workers run under ([orca.md](orca.md#fallback-to-supervised)).

1. `'<claude path>' --version` is v2.1.330 or later; after a failure the fallback starts no Claude Code worker either ([orca.md](orca.md#start-the-run)).
2. `worker-settings.mjs` wrote the worker's settings file right before the start ([Automatic bounds](modes.md#automatic-bounds)) and exited 0. A hand-made file can keep a placeholder or a wrong path and still load, with its deny rules pointing nowhere. Then, as the last command before Orca starts the worker's session, `node <skill folder>/worker-settings.mjs --check` with the same arguments exits 0: it reads the file as it is then and passes only the exact text the script writes for that worktree and that project. Claude Code starts with an empty settings file as with none, so without the deny rules and the file-tool bounds. Any other exit starts no worker: it makes the item BLOCKED, and for the probe it fails check 5.
3. `node <skill folder>/start-checks.mjs --project <project path> --worktree <worktree path>` takes checks 3 and 4 (`--config-dir <folder>` for a worker whose Claude Code configuration folder is not `$CLAUDE_CONFIG_DIR` or `~/.claude`). Exit 0 passes what the script reads; mods and managed settings from device management or the server stay your read. 1 fails, `failed` naming each entry, also for an unreadable file. 2 leaves `read` and `unresolved` to you: read the file each command runs and what each entry names; one you cannot judge fails its check. `unresolved` names what the script does not read: a settings or marketplace key not known to run no command, an `Edit`, `MultiEdit`, `Write` or `NotebookEdit` allow rule outside the worktree, a skill, agent or command file whose frontmatter sets `hooks` or `mcpServers` or opens with an indented line, a `skills`, `agents` or `commands` folder in the `.claude` folder of a subfolder of the worktree (it loads when the worker works there; `node_modules` and `.git` are not searched), a plugin in `<config dir>/skills/`, `.claude/skills/` or `<config dir>/plugins/synced/`, `CLAUDE_CODE_PLUGIN_DIRS`, `CLAUDE_CODE_PLUGIN_CACHE_DIR`; a `--plugin-dir` plugin stays your read. Check 3: no hook, MCP or LSP server, monitor, command setting (status line, `apiKeyHelper` and the like) or `env` of check 4's settings files, `managed-mcp.json`, `.claude.json`, either checkout's `.mcp.json` or an enabled plugin, and no process an enabled mod starts, runs a file inside the repository or a tool that loads the repository's code or configuration (a formatter, a linter, a package script): these run outside the permission rules and the role guard, so a worker that edits such a file gets its code run past them. The script fails a command that names the repository, a relative path or `CLAUDE_PROJECT_DIR`, or runs a known such tool, and lists the others in `read`, with each hook that is no command hook.
4. No entry that defeats a bound, in managed settings, the user settings, or either checkout's `.claude/settings.json` or `.claude/settings.local.json`: a `permissions.additionalDirectories` entry outside the worktree; `disableAutoMode` or `permissions.disableAutoMode`, which keeps the worker out of auto mode; `disableAllHooks` or `allowManagedHooksOnly`, which turn off the role guard; an `env` that sets `CEDARLOOM_ROLE`, which an automatic worker runs without; a `sandbox` key whose `enabled` is not `false`: CedarLoom ignores the Claude Code sandbox and does not support it, so turn it off or remove the key. In managed and user settings, `unresolved` names an `autoMode.allow` or `autoMode.environment` entry other than `"$defaults"`, which widens what auto mode's classifier lets pass, and an `autoMode` list without `"$defaults"`, which drops the classifier's built-in rules. Name in the run report the other allow rules of those files: `allowRules`, and each `autoMode.classifyAllShell` value: `classifyAllShell`.
5. The probe: one worker with the same launch in a scratch worktree of the project (create `.husky/` there first), its spec these steps. Check each result yourself where you can.
   1. Version: as check 1.
   2. The Write and Read tools on a new file in the run folder are refused, and no file appears there. The Write refusal names `blockWritesOutsideWorkingDirectories`, which shows the settings file loaded.
   3. The Write tool on `.claude/settings.json`, `.mcp.json`, `.husky/pre-commit`, `.envrc`, `.npmrc` and `.git` is refused.
   4. Mode and role: the probe's terminal shows auto mode. `printenv CEDARLOOM_ROLE` passes the Role check of [orca.md](orca.md#start-the-run) (the role guard refuses it, and it prints nothing). `git -C <worktree path> push --dry-run origin HEAD:refs/heads/<default branch>` is refused by the role guard, its message naming the default branch.
   5. A write in the worktree and `git add` succeed; `git push origin HEAD:refs/heads/probe/<r>` and `gh pr list` are refused by the deny rules. Then, as the coordinator ([Commit and push](commit-and-push.md)): `commit-push.mjs sync` with `--branch probe/<r>` exits 1 with `step 4: origin has no branch probe/<r>`, and `commit-push.mjs commit` with `--dry-run` and no `--title` exits 0.

Pass rule: every step as stated, and the probe's report arrives as its final answer, read through Orca as [Worker reports](orca-messages.md#worker-reports) says; no report within `stallMinutes` fails it. The probe tests the settings file, the mode and the role guard, not what auto mode's classifier lets pass or the isolated environment. The bounds that hold are those four: the classifier, the deny rules, the role guard as a backstop for the commands it can read, and the isolated environment for what a Bash command reaches ([Automatic bounds](modes.md#automatic-bounds)). After the probe, first and without git, give `.git` its content back if a passing step 3 changed it. Then remove the scratch worktree as an automatic worker's ([Clean up](orca-clean-up.md)), with `--force`, once you have read the files it still holds: without it the removal refuses a worktree with changes, untracked or staged, such as the probe's file when the probe ended before step 5's commit, or a file a passing step 3 made. Every worker's worktree is removed without `--force`. Then delete the branch `probe/<r>`: its commit is the probe's, never pushed.
