# Project bot run

The procedure of every project bot automation but the catch-up sweep. [SOUL.md](SOUL.md) holds first. `<state>` is `<bot home>/state/`, `<clone>` the bot's checkout of the repository (`project` of a state file), `<skill folder>` this file's folder, and `ORCA` the Orca executable as [orca.md](orca.md) says. The steps of [SKILL.md](SKILL.md), [review-and-merge.md](review-and-merge.md) and [orca.md](orca.md) that this file names apply with the changes below.

## Every run

1. **Run folder.** Take a new run id, the UTC start time as `YYYYMMDDTHHMMSSZ`, `-` and six random hex digits (`openssl rand -hex 3`), and make `.cedarloom/runs/<run id>/` in the bot home with `mkdir` without `-p` (a folder that exists takes a new id), the run's working folder: specs, thread files, approvals and prompts go there, since `thread.mjs` and `approval.mjs` write only there. Delete it when the run ends, but for a file a report names.
2. **Count.** `state.mjs` has no command line: call its functions with `node --input-type=module -e "<code>"` that imports `<skill folder>/state.mjs`. First `count(<state>, new Date())` reads today's counts. At 320 runs or 120 worker starts, start nothing and end. A run about pull request `<n>` that already has 12 runs today counts `{ runs: 1 }` and ends: it gets no further run that UTC day, and the catch-up skips it too. Where its state's `cappedOn` is not that day, set `cappedOn` to the day, then name the cap in the run's report, never in an approval issue; unlike `held`, it ends with the day. Otherwise record the start, `count(<state>, new Date(), { runs: 1, pr: <n> })` (no `pr` for a run about no pull request). Right before each start of a worker or role bot run, read the counts again: at 120 worker starts, start no more; else add `{ workerStarts: 1 }`. A throw stops the run: report it.
3. **State.** Read `pr-<n>.json` with `readState` (rebuilt as [SOUL.md](SOUL.md) says when missing or unreadable: a file that exists and gives `null`). End when `handled` names the event's head with an action that already answers this event (`fix` for a red head or conflict; `merge`, `trial` or `update` for a green one) and no answer of the owner is new: a green event on a head handled as `fix` goes on. A `held` pull request gets nothing but its owner's answer.
4. **End.** Write the state with `writeState` after each decision: read the file again right before and change only that decision's fields, so no older read replaces `mergeCommandAt`, `held` or `mergedAt`. The report goes where the automation's `--results-to` sends it: `chat` for every project bot automation, never `thread`, which posts it on the pull request.

A decision taken on the owner's behalf is named with its source (file and line) in the comment or report that acts on it. Mark one `(owner)` only for the answer `approval.mjs answer` reads.

## Pick

The pick sweep runs every 30 minutes with `--precheck "node <skill folder>/precheck.mjs <clone>"`. Run the precheck again and take step 1 of the Loop ([SKILL.md](SKILL.md#loop)) on the issues it prints, oldest first, within `workersPerProject`, `hostWorkerLimit` and three starts per run. For each: thread file, outcome checks, depth and risk class, then the spec from [spec-template.md](spec-template.md). A deep issue, or one that leaves its approach open, first gets a planner run unless it has a plan, from that run's report or its answered `design` approval; a deep or high one without that answer gets its `design` approval, with any plan, and no worker. `cl:in-progress` goes on right before a start. Before the precheck, a prompt file with its result file is that run's report ([Reports and mail](#reports-and-mail)); one older than `stallMinutes` without it is stalled: report it, and delete the prompt file unless its issue carries `cl:in-progress`, which stays for the owner.

Before a start of an automatic worker, check 2 of [Automatic start](modes.md#automatic-start) runs; the others are the daily probe of the catch-up run ([bot-catch-up.md](bot-catch-up.md)). Without a passed probe for the UTC day in `<state>/probe-<day>.json`, start the project supervised that day where [orca.md](orca.md#fallback-to-supervised) offers it, else start nothing.

## Start

- **Host limit.** Before each start, count the working workers machine-wide as [Host limit](orca.md#host-limit) says, and add each role bot run of this repository that has no `result` in a state file's `runs`, and each prompt file without its result: planner, worker and maintainer runs have no state file.
- **Role bot run.** Write its prompt to the file `<bot home>/prompts/<name>.md`, `<name>` being `<repo>-<n>-<role>-<round>-<run id>-<k>` (`maintain` for `<n>`) and `<k>` this run's start count from 1, so no spec or thread text is typed and no two runs share a file: the role's procedure file `bot-<role>.md` first, then the filled spec (planner, worker), the reviewer brief of [Review](review-and-merge.md#review) (reviewer), the follow-up (fixer) or the automation's `<maintain folder>` and `<state>/maintain.json` (maintainer), and the result file the run writes its report to with the file tool, `<role bot home>/results/<name>.md`. Both bots run on one host, each able to read the other's file. Then a one-time automation on that bot: `ORCA automations create --bot <role bot> --name '<owner/repo>#<n> <role> <round>' --model <model> --effort <effort> --runs-in new --results-to none --once --by <UTC now plus one minute> --prompt 'Read <skill folder>/SOUL.md, then the prompt file <its absolute path>.' --json`, `<role bot>` being `<repo>-<role>`. Orca deletes the automation after its run; delete the prompt file once its result is in.
- **Fresh worker.** Where the repository has no role bots, or `docs/agents/bots.md` names fresh workers for the role, start an Orca worker with that prompt in its project's mode as [Start the run](orca.md#start-the-run) says, with its launch line, `--permission-mode` and settings file.
- **Record** `{ startedAt, head, role, resultFile, result: null }`, the head the run starts for, its role and the result file's absolute path, in the state's `runs` (a role bot run) or `dispatches` (an Orca worker), and the automation ids in `rules`.

## Reports and mail

- A worker's first report with a pushed branch. A worker bot's branch: check its files as the end of [bot-worker.md](bot-worker.md) says, then open the draft from a file, so no reported text is typed: write `{ "title", "head": <branch>, "base": <default branch>, "body", "draft": true }` to `pr.json` in the run folder, the body as step 3 of [Commit and push](modes.md#commit-and-push) says, and run `gh api repos/<owner/repo>/pulls -X POST --input <its path>`. An Orca worker's change: `node <skill folder>/commit-push.mjs commit` for an automatic worker, `commit-push.mjs supervised` for a supervised Claude Code worker. Then write `pr-<n>.json` (repo, pr, issue, branch, project, round 1, a worker bot run in `runs`) and the event rules, each `--runs-in new --results-to chat` with this file in its prompt: `<owner/repo>#<n> ci_passed` on `github.ci_passed subject=<owner/repo>#<n>`, and the same for `ci_failed` and `pr_conflicted`.
- Each result goes into its `runs` or `dispatches` entry. A reviewer's report whose Head line names another head than its entry's `head` is no review: start a new reviewer run for the entry's head. One without a Head line or verdict (the head is gone, a read was refused) is no review and starts nothing: where the pull request's head is still the entry's `head`, the review is the owner's ([Review](review-and-merge.md#review)), filed once as `held` (`no review of <head>`). Otherwise its verdict becomes the review of record ([Review of record](review-and-merge.md#review-of-record)), posted from a file; record `reviewedHead`, `reviewUrl` and `round`. Findings go to a fixer run ([Rounds](review-and-merge.md#rounds)); a `void` review gets a new reviewer run for that head, and a verdict with no Blocking or Important finding goes on in this run as Green accepted head. A fixer's report: reply on each review thread it names with its fix commit or evidence, from a file, through the `pre-merge.json` command. A worker's question is answered from written sources only, naming the source; an owner-only one is filed as an approval, and the answer goes to a new run.
- A planner's report: its questions as a worker's, then `cl:in-progress` off and [Pick](#pick) on its issue, where an owner question is open in the run acting on its answer. A maintainer's: [Maintenance](#maintenance) step 2.
- Release and clean up a finished Orca worker as [Clean up](orca.md#clean-up) says. A role bot run deletes its own clone; one its report names as left is deleted with the pull request's clones.

## Pull request events

- **Green head, not reviewed.** Claim it: `mkdir <state>/claim-<n>-<head>`. An existing folder younger than `stallMinutes` means another run has it: end. An older one is stale: where a reviewer entry of `runs` or `dispatches` for that head has no `result`, take condition 7 of [bot-catch-up.md](bot-catch-up.md) for it in place of this step; else `rmdir` the folder and claim again. Then the claim comment, then a reviewer run at the level of [Sensitive or routine](review-and-merge.md#sensitive-or-routine): a first review, or the re-review of [Rounds](review-and-merge.md#rounds) where `reviewedHead` is set. Its report comes back as [Reports and mail](#reports-and-mail) says.
- **Red head or conflict** that `handled` does not name: one fixer run for that head; record `handled` `{ head, action: "fix" }`.
- **Green accepted head**, accepted when the conditions of [Ready](review-and-merge.md#ready) hold, the last review read from the review of record at the state's `reviewUrl`, never from another comment: Ready, then Merge below. Verdict `update`: `gh pr update-branch <n> -R <owner/repo>`, record `updatedAt` and `handled` `{ head, action: "update" }`, end; the new head's event takes it on.

## Merge

Take steps 1 to 5.2 of [Merge](review-and-merge.md#merge) in the PR's newest clone, writing the subject and body files as `<state>/pr-<n>-subject.txt` and `pr-<n>-body.md`, a trial's base as `trialBase`. Record the accepted head and the verdict's `next` (`merge` or `trial`) in `handled`, that clone's absolute path as the last entry of `clones`, and the risk class the review used (`low`, `medium` or `high`) as `riskClass`, then run `node <skill folder>/merge.mjs <state>/pr-<n>.json --run <run id>` once (`--method` only for a method `AGENTS.md` names). Its answer:

- `merged`: delete the PR's event rules and clones, and its branch as [Clean up](SKILL.md#clean-up) says; where the policy's `closeIssue` is true, check its issue closed ([Outcomes](SKILL.md#outcomes)).
- `wait`: end; a later event or sweep retries.
- `redMain`: end; the catch-up run reports the red tip.
- `restart`: steps 1 to 5.2 once more in this run; a second `restart` ends it.
- `stop`: file the reason once to the owner, as `held` where the script did not set it. A state with `mergedAt` (a head nobody reviewed merged) also gets the cleanup of `merged`. Exit 1 goes in the report too.

A merge command that is held or has no merge log line (`mergeCommandAt` set) pauses every merge of the repository until the owner's answer; a pull request held for any other reason blocks only itself. The run that reads that answer clears `held` and `mergeCommandAt` together, in one `writeState`.

## Maintenance

The weekly automation, where a maintainer bot or its fallback exists:

1. **Answer.** On a `maintain` question answered in the local queue (`approval.mjs queue`) that `answered.json` does not list, name each of its findings in `<state>/maintain.json` by its id with `writeState`, then list the question in `answered.json`. A private repository: file each approved one as an issue without `startLabel`: behavior-preserving, tests unchanged, normal review; its number goes in after: one without a number is reported, never filed again. Any other visibility: list them for the owner.
2. **Findings.** A maintainer result: one that names a security weakness goes into the report only; the others, if any, as one `maintain` question, filed in the local queue only (`approval.mjs file`), options (a) all, (b) those the answer lists, (c) Hold. Delete its prompt file.
3. **Start.** No open `maintain` question and no maintainer prompt file: one maintainer run ([Start](#start)) at `models.worker` for `deep`; it counts as a worker start.

## Reconciliation

The daily automation takes the [Reconciliation](SKILL.md#reconciliation) with `node <skill folder>/reconcile.mjs --project <clone> --repo <owner/repo> --default-branch <default branch> --log <state>/merge-log.md`. Also report each event rule of a closed pull request (`ORCA automations list --json`), each UTC day without a catch-up run (no `counts-<day>.json` with `catchUp` above 0), and each prompt file older than `stallMinutes`. It changes nothing.
