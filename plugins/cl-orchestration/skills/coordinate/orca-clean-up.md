# Clean up

The release of a worker and the removal of its worktree.

```text
ORCA orchestration worker-release --dispatch <dispatch id> --json
ORCA worktree rm --worktree path:<worktree path> --run-hooks --json
```

The second command removes a supervised worker's worktree; an automatic worker's goes as the worktree list below says. Before it, delete a supervised Claude Code worker's rule file, `<worktree path>/.claude/settings.local.json`: the file is ignored, not untracked (unverified: whether an ignored file blocks the removal). Orca does not force the removal: any untracked file blocks it (`Failed to delete worktree at <worktree>. ?? .env`, Orca 1.4.254). Then leave the worktree, never pass `--force` or delete the file, and name the path and the files in the report. `--run-hooks` runs the project's `orca.yaml` archive script before the removal. When the removal fails on that script, remove the containers below first and run it again. After the removal, list what is left (`podman ps -aq --filter label=devcontainer.local_folder=<worktree path>`, or `docker`) and remove those containers with `rm -f`.

A worker whose terminal a person typed in gets no cleanup ([SKILL.md](SKILL.md#rules) has the rule). It gets no follow-up either: its pull request's findings go to the owner. With Orca, such a worker's `worker-read` output shows input that neither a `send`, a dispatch of the coordinator (the start, a follow-up) nor its `terminal create --command` launch line carried. Keep it with `ORCA orchestration worker-retain --dispatch <dispatch id> --json`: no stop, no release, no worktree removal. At the wake-up for each report of a supervised Claude Code worker, `worker-read` it first and run `worker-retain` when it shows such input; once it is released, nothing further is done and its worktree stays. The owner's answer to a dialog there, in that terminal or through Orca's approval ([A permission dialog](orca-watch.md#a-permission-dialog)), leaves the worker the coordinator's; any other text typed there makes it a person's (unverified: whether `worker-read` shows such an answer as input). Orca's `send` is the coordinator's message command and, with the starts of [Start the run](orca.md), the only way into a worker terminal ([SKILL.md](SKILL.md#rules) has the rule).

Release:

- Release only a settled worker, so stop an idle worker that sent no report (for an automatic worker, no final answer) before releasing it.
- A supervised Claude Code worker stays open for follow-ups ([Start the run](orca.md)) and is released once its pull request is merged or left for the owner, or earlier when a step needs it released ([outcomes.md](outcomes.md), Blocked; [Clean up](run-files.md#clean-up), step 1; a fresh start on its branch). A worker a person typed in gets none, so `worker-read` it again right before the release, as at its report. Its release is an automatic worker's (below): `terminal close`, confirmed by `terminal list`, then `worker-release`, which reports `retained`; Orca then marks the dispatch failed with `Terminal closed by operator request`, which changes no outcome. When the close fails or the terminal is still listed, keep its rule file and worktree, and name the worker and its terminal in the report.
- A Codex worker with a pull request is released after the merge, or once the pull request is left for the owner, not before.
- An automatic worker is released as soon as its report arrives, before Commit and push ([Automatic bounds](modes.md#automatic-bounds)); the release keeps its worktree. Run `ORCA terminal close --terminal <terminal> --json`, then `worker-release`, which reports `retained` (Orca 1.4.254). The worker counts as released once `ORCA terminal list --worktree path:<worktree path> --json` no longer lists that terminal. Orca then marks the dispatch failed with `Terminal closed by operator request` and escalates it as lost (Orca 1.4.259): that is expected and changes neither the outcome its final answer gave nor the release. Do the same for each follow-up's terminal. When the close fails or the terminal is still listed, name the worker and its terminal in the report. Unverified: whether a process the worker detached from its terminal outlives the close.
- `worker-read` still returns a released worker's output.

The worktree:

- `ORCA worktree rm` is for a supervised worker's worktree only, never for an automatic worker's, the probe's scratch worktree included. Orca runs its own git commands for the removal, without the pins and the `commondir` read of [Commit and push](commit-and-push.md), and `--run-hooks` runs the archive script, all in your session: a hook, a monitor or an `orca.yaml` that the worker wrote in its worktree could run there. Unverified: which git commands Orca runs in the worktree, and whether it reads `orca.yaml` from the worktree or from the main checkout (`ORCA worktree rm --help` states neither).
- `ORCA worktree rm` keeps the local branch, also with `--force`, unless `--delete-branch` is passed, which the command above does not (`ORCA worktree rm --help`, Orca 1.4.259; the branches stayed with Orca 1.4.254). An older host keeps its own branch policy and prints a warning: name such a warning in the report.
- Never remove a blocked worker's worktree.
- An automatic worker's worktree goes with `worktree remove`, which leaves the branch (an entry Orca's worktree list keeps: below): first the `commondir` read of [Commit and push](commit-and-push.md), then `gitW worktree remove "<worktree path>"`, hook disables included, `-C "<project path>"` for `-C <W>`. The removal runs `git status` in the worktree, which can run a hook or a monitor of the worktree, and `-c` reaches that child process too. Its archive script does not run: its containers go by the listing above.
- A worktree that Orca's Workspace Cleanup already removed counts as removed: `git -C <project path> worktree list --porcelain` prints no `worktree <worktree path>` line and the folder is gone. Run no `ORCA worktree rm` for it; its containers still go by the listing above. Workspace Cleanup is an Orca setting with every rule off by default, and it spares a workspace active in the last hour or with a running terminal, a live agent, uncommitted changes, unpushed commits or, by default, ignored files such as a rule file (Orca 1.4.259, `src/shared/workspace-cleanup/workspace-cleanup-policy.ts` lines 54-63, `src/shared/workspace-cleanup/workspace-cleanup-evaluation.ts` lines 9, 65-77 and 180-186).
- The remote branch and the local branches either removal leaves: [run-files.md](run-files.md#clean-up), step 3.

Before the coordinator turn ends, `ORCA orchestration worker-list --run <run id> --terminal-state reclaimable --json` returns no worker but a worker whose terminal a person typed in, which stays (above). The same list with `--terminal-state retained` shows the kept-open workers ([Host limit](orca.md#host-limit)): each settled one in it (`outcome` other than `in_progress`) is a Codex or supervised Claude Code worker whose pull request is in review or merge, or a worker whose terminal a person typed in. An automatic worker is not kept open after its report. It, and a supervised Claude Code worker after its release, can still appear in that list, its dispatch marked failed once its terminal is closed (Release), and it counts as released once its terminal close is confirmed, as Release says. `worker-release` removes no worktree, and an automatic worker's stays after its release until its pull request is merged or left for the owner. So a worktree still listed by `ORCA worktree list` past that point (for a worker without a pull request, past its settling), a blocked worker's, or one whose removal an untracked file blocked (above), aside, is the step above not run, unless git no longer has it: `git -C <project path> worktree list --porcelain` prints no `worktree <worktree path>` line and the folder is gone. Such an entry is Orca's record alone (unverified: whether Orca drops it after `git worktree remove`, not measured): leave it, never run `ORCA worktree rm` on an automatic worker's entry, and name its path in the report.
