# Outcomes

Contents: the six outcomes, a pull request left open, a refused hook, follow-ups.

A worker's outcome comes from its report and the handoff block in its report (outcome, what changed, checks and results, open risks, next step), in a batch per issue from its status message ([Batches](spec-template.md#batches)), never from reading its terminal. Record the decisions a report or its pull request lists in `## Decisions`; one that is owner-only ([Owner-only decisions](decisions.md#owner-only-decisions)) is a gate, and its pull request stays a draft until the owner's answer. An automatic worker's report is its final answer, which Orca hands on ([Worker reports](orca-messages.md#worker-reports)), and names a staged change: release it at once, which keeps its worktree ([Automatic bounds](modes.md#automatic-bounds)), then commit, push and open its draft PR by [Commit and push](commit-and-push.md). A supervised Claude Code worker on Orca reports a commit: first check it for a person's input ([Clean up](orca-clean-up.md)), then push it and open its draft PR by the same section. What either would comment on an issue or a review thread is in its report or answer, for you to post ([spec-template.md](spec-template.md)). Copy the handoff into the run folder before cleaning up.

- **Done with a PR**: review by [review.md](review.md), ready and merge by [merge.md](merge.md), which says when a PR stays open for the owner; until one of the two, a supervised Claude Code worker stays open and takes each follow-up in its own session, or as a new start in its worktree when it is released, its terminal is gone or its terminal shows no auto mode (a `follow_up` not confirmed in its own terminal is kept for the owner, with nothing stopped or started), and a Codex worker stays unreleased for follow-ups ([Start the run](orca.md#start-the-run)); an automatic worker was released at its report, and each follow-up of it is a new start. After the merge, when `closeIssue`, at the next wake-up read the issue's state (`gh issue view <number> -R <owner/repo> --json state`): its PR's `Closes` line closes it at the merge ([Ready](merge.md#ready)), and one GitHub left open you close, with a comment linking the PR (unverified: whether a merge through a merge queue closes linked issues). A PR of a split batch ([Needs replan](#outcomes)) closes nothing: its issue closes by that batch's rule. Clean up after the merge, without waiting for that read.
- **Done, no change needed**: verify the claim yourself on the base branch (read the code, run the check the issue names). Comment the evidence on the issue and close it when `closeIssue`. Then clean up.
- **Blocked**: the worker commented on the issue and reported BLOCKED (a refused hook, a missing credential, a check it cannot fix). Confirm the comment exists in a rerun of the thread file, release the worker (a batch's: [Batches](spec-template.md#batches)), start the next issue of that project. Keep that worktree and branch, and list the issue in the report: they may hold the only copy of the work. Where its pull request is open, take a `Closes` line out of its body, since it closes the issue at any merge: write the body without that line to a file in the run folder with the file tool, run `gh pr edit <n> -R <owner/repo> --body-file <file>`, and name the pull request in the report too. A report with an owner-only question is a gate ([Owner-only decisions](decisions.md#owner-only-decisions)).
- **Needs replan**: the worker found the spec does not fit the issue. Never restart it with the same spec. When the handoff block's next step stays inside the issue's text and the policy, write one new spec from the template with it; otherwise list the issue for the owner. One replan per issue and run.
  - Work that splits into several PRs: the worker posted its PR list on the issue, each PR with its goal and files; read it in a rerun of the thread file. Approve it with a comment on the issue only when every PR stays inside the issue's text, the spec's Owned paths and the policy; then write the new spec as a batch of those PRs in the list's order, one branch per PR by [Names](brief-reference.md#names) with its own slug, and the approved list under `Shared context:`. Otherwise list the issue and the PRs for the owner.
  - In such a batch the unit is the PR, not the issue: one draft PR per branch and one status message per PR ([Batches](spec-template.md#batches)), and the issue closes by `closeIssue` only after every PR of the approved list is merged, in any order.
- **Failed**: the worker reported failure without BLOCKED or NEEDS_REPLAN, or an automatic worker's final answer names no outcome ([Worker reports](orca-messages.md#worker-reports)). Read the worker's output. Retry once with a fresh worker and a spec from the template, unless the item had its one retry ([Stops](orca-messages.md#stops)); a failure after it is blocked.
- **Stalled**: no commit, PR or message for `stallMinutes`, and no escalation from Orca still unhandled: one that reports a stop, an exit or a loss without a report goes by [Stops](orca-messages.md#stops), which also says how a worker it left idle is checked. Read the worker's last output. Only proof that the session ended without a report (its final turn is over and nothing was sent; for an automatic worker, its final turn holds no final answer) makes it blocked, after stopping it. A worker still producing output keeps waiting.

An issue whose pull request stays open after Blocked, Needs replan, or a Failed or Stalled worker made blocked loses its `Closes` line the way Blocked says. A later start or follow-up that continues that pull request for the whole issue (a new spec of Needs replan, the owner's answer) puts it back at its report, the body carrying the line as the first round's did ([Commit and push](commit-and-push.md)): you set it with `gh pr edit` where you open the pull request (automatic, supervised Claude Code on Orca), and a worker that pushes updates its own. The [Ready](merge.md#ready) check expects it once that worker reports DONE.

A refused commit or push by a repository hook is reported with paths and counts only and handed to the owner; the hook stays as it is ([Rules](SOUL.md#rules)).

Follow-ups, work found outside a task, reach you in reports (a worker's handoff block, a reviewer's result); you file an issue for one only when you sort them (below). Collect each in `follow-ups.md` of the run folder, in your own words with its project and the files it touches. At each [Reconciliation](run-files.md#reconciliation), daily and at the run's close (its step 6), and in a `keepRunning` run whenever a project has no worker active and no issue to pick, sort that project's unmarked follow-ups once, each staying in that file marked with where it went (the report, or its issue's reference), for the report's list:
- One that names a security weakness goes into the report only, never into an issue or a comment: reporting it by the project's security policy is the owner's.
- One that an open issue covers (`gh issue list -R <owner/repo> --state open --limit 1000`, a follow-up filed before a stop among them) goes into the report with that issue's reference, never into a comment on it: a comment under the owner's login would reach that issue's next worker as trusted text.
- The others, each worth one pull request, grouped by the code they touch: when `gh repo view <owner/repo> --json visibility` prints `PRIVATE`, file each with `gh issue create -R <owner/repo> --title '<title>' --body-file <file> --label cl:follow-up`, titled by [Labels and title](approvals.md#labels-and-title), and list it for the owner; where filing fails (no `cl:follow-up` label, issues off, no permission), it goes into the report. Any other visibility, or a failed command: no issue (it could show run context); each goes into the report.
- One too small for a pull request of its own goes into the report.
- Add no `startLabel`: the owner chooses the work.
