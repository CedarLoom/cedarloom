# Orca follow-ups

A follow-up to a worker of this run. `ORCA` and the Orca guide are as [orca.md](orca.md) says.

A follow-up to a worker of this run, a supervised one, an automatic one released at its report ([SKILL.md](SKILL.md#loop), step 3), has its text in a file. A follow-up to a worker that runs Orca commands starts with the spec's Chat name line, its role `fixer`:

- A supervised worker, Claude Code or Codex, gets it as a message to its newest dispatch, a Claude Code one only while it is kept open (below). Orca makes a reported or released worker's message a follow-up task, which it reports with `worker_done` (Orca's guide):

  ```text
  ORCA orchestration send --to dispatch:<dispatch id> --subject "Follow-up" --body "$(cat <follow-up file>)" --json
  ```

  A supervised Claude Code worker gets it only in place, in the session its launch started. Before each follow-up, write its rule file and read it with `--check` again, as before its start ([Worker rules](modes.md#worker-rules)): a failure sends nothing and makes the item BLOCKED. Its follow-up file carries the Role check line in its follow-up form ([Start the run](orca.md#start-the-run)). Then confirm that `ORCA terminal list --worktree path:<worktree path> --json` lists the worker's terminal, that `worker-show` reads the newest dispatch as unreleased, that `worker-read` shows no person's input ([Clean up](orca-clean-up.md#clean-up)), and that `ORCA orchestration worker-read --dispatch <dispatch id> --source terminal --limit 50 --json` shows Claude Code's input box with `auto mode on` in its status bar ([permission modes](https://code.claude.com/docs/en/permission-modes)). The read's last non-empty line decides: it must be that status bar, and a shell prompt there, also below an earlier status bar, is an agent that exited (unverified: that the read shows the status bar, and as its last line). Only then `send`, and the expected answer is `delivery` `follow_up` with the worker's own terminal, the one `terminal create` returned, as its `terminal` (unverified: that the answer names it), delivered into the same session (unverified for a worker in a terminal). A `follow_up` is accepted as in place only when the answer names that terminal, or names none and `terminal.handle` of `worker-show` of the new dispatch is that terminal (unverified: that `worker-show` names the terminal a follow-up dispatch went to), and `terminal list` still lists it. Every other `follow_up` (another terminal named, none named, the worker's own no longer listed, a read that fails) may run in a tab where a person resumed the worker's conversation (below), so the worker counts as one whose terminal a person typed in ([Clean up](orca-clean-up.md#clean-up)): `worker-retain` the new dispatch, with no stop, close, release, retry or new start, write it into the handoff file's `## Open` as such a worker (the issue, the kept dispatch id, the terminal named, if any, and the worktree path), tell the owner at once, and the item waits for the owner (unverified: `worker-retain` on such a dispatch, not tried in a live run). When the checks before the `send` find the worker released or its terminal gone, send nothing: the follow-up is a new start with the lines of [Start the run](orca.md#start-the-run) in the same worktree, the follow-up file holding the filled spec, then the follow-up, as for an automatic worker (below). When the read shows no auto mode, send nothing either, and stop the worker only on proof that no dialog holds it and no turn runs: `worker-show --full` reports `observation.agentWait` as null, the field present (a missing one means Orca did not look: [A permission dialog](orca-watch.md#a-permission-dialog)), and the read ends in a shell prompt, or shows the agent idle at an empty prompt, neither loading nor working, with another mode in its status bar. Then `worker-stop` its newest dispatch unless that one already reported, and once the stop is confirmed close its terminal (`ORCA terminal close --terminal <terminal> --json`, confirmed by `terminal list`) and `worker-release` it, then make that new start. Its commits and changes stay for the new worker to review. A stop or close that is not confirmed starts nothing: name the worker and its terminal in the report, and the item waits for the owner. Without that proof nothing is stopped or closed, and the follow-up waits with the item: a dialog, listed for the owner yet or not, is handled as Held at a dialog says ([Acknowledgement](orca-messages.md#acknowledgement)), and any other screen, a worker in a turn included, is read again at the next wake-up.

  A reopened or fresh-started session is never accepted. A resumed Claude Code session can start in another mode than the launch line gave: a session that ended in Manual resumes in the `defaultMode` of a settings file when one takes effect, and flags on the resume line override the stored mode ([sessions](https://code.claude.com/docs/en/sessions)); how Orca's reopen builds its line is not documented. So when a `send` returns `delivery` `reopened` or `started_fresh`, `worker-stop` that new dispatch at once, and once the stop is confirmed close its terminal when `worker-show` names one, and the worker's earlier terminal when `terminal list` still lists it (`ORCA terminal close --terminal <terminal> --json`, confirmed by `terminal list`), `worker-release` it, then make a new start with the lines of [Start the run](orca.md#start-the-run), as for a released worker. Its commits and changes stay for the new worker to review; name the event in the report. Orca delivers a terminal worker's follow-up in place only while the agent runs in its live terminal; otherwise it closes the leftover shell and reopens the worker through its own launch, or delivers a `follow_up` into a tab where a person resumed the worker's conversation (Orca 1.4.259, `src/main/runtime/rpc/methods/orchestration/worker/follow-up/worker-follow-up-choice.ts` lines 80-99, 115-147 and 189-205). The terminal read before the `send` sees an agent that exited; one that exits after that read is still reopened, so the check makes this rare, not impossible.

  A worker still working, a batch on its next issue, gets the message when its turn ends, with no follow-up task.

  A refused `send` sent nothing. Send it again after `worker_unverifiable` once `worker-show` reads the worker; after `worker_not_restartable` or `worker_workspace_gone` the follow-up is a new start by [SKILL.md](SKILL.md#loop), step 3.
- An automatic worker was released at its report, its worktree kept ([Clean up](orca-clean-up.md#clean-up)), so its follow-up is a new start: a fresh session in a new terminal of the same worktree, as at the start, with its settings file written again and read with `--check`, the follow-up file holding the filled spec, then the follow-up. Its old terminal would not take it anyway: Orca recognises a released worker's terminal for its first dispatch only. Where Workspace Cleanup removed that worktree, the follow-up is a new start by [SKILL.md](SKILL.md#loop), step 3.

A worker on `fable` that already reported gets no follow-up: release it and start a fresh worker on the branch ([SKILL.md](SKILL.md#rules)) by [SKILL.md](SKILL.md#loop), step 3. Such a follow-up counts like a start ([Host limit](orca.md#host-limit)).
