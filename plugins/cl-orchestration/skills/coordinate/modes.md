# Worker modes

The two modes, their gates, the rule file of a Claude Code worker and the sandbox of an automatic one: [Modes](#modes), [Gates](#gates), [Worker rules](#worker-rules), [Sandbox on](#sandbox-on). The checks before an automatic worker starts are in [automatic-start.md](automatic-start.md), the coordinator's commit and push of a worker's change in [commit-and-push.md](commit-and-push.md).

## Modes

Each project's `mode` comes from its policy ([policy.md](policy.md)). A leading `--mode supervised` run argument lowers every project of the run to supervised; nothing raises a mode. The handoff's `Mode:` line holds each project's mode for the run and, where lower than its policy's, why; a resumed run keeps it.

- **Supervised:** a Claude Code worker starts in auto mode (`--permission-mode auto`, Manual where auto mode is unavailable) in a terminal the coordinator makes, with the rule file of [Worker rules](#worker-rules); another agent's worker starts through Orca's own launch, so its prompts depend on Orca's agent permission setting, the user's choice ([orca.md](orca.md#start-the-run)). The coordinator writes no flag that bypasses or skips permission prompts; a worker's prompts are the owner's ([A permission dialog](orca-watch.md#a-permission-dialog)).
- **Automatic:** a Claude Code worker starts only with the sandbox on (below), with `--permission-mode dontAsk` and `--settings <run folder>/settings/<id>.json` on its launch, the absolute path that the `--check` read of [Automatic start](automatic-start.md) took; a call the bounds and allow rules do not cover is denied, never prompted. No flag that bypasses permission prompts, in any form, and its settings file sets `disableBypassPermissionsMode` to `"disable"` ([settings](https://code.claude.com/docs/en/settings)), so a hook cannot switch the session to bypass mode either ([changelog](https://code.claude.com/docs/en/changelog)). A worker takes one issue, whatever `issuesPerWorker` says: it cannot commit, so it cannot switch branches. Its spec changes as [spec-variants.md](spec-variants.md#automatic-mode) says.

`dontAsk` only refuses tool calls that no allow rule lists; it decides no question: an owner-only decision is a gate ([Gates](#gates)).

### Gates

A gate holds one item for the owner while the other items go on ([Owner-only decisions](decisions.md#owner-only-decisions)): in supervised mode every question put to the owner, in automatic mode an owner-only decision only.

- Worker side: the worker never decides an owner-only question and never takes a default for it, also where a tool call would pass. With a question command and in supervised mode it asks and waits for the answer; otherwise it stops that item and reports BLOCKED with the question ([spec-template.md](spec-template.md)).
- Coordinator side: put each such question to the owner once, in your own words, as an approval whose What starts with `question` and names the issue and the decision ([approvals.md](approvals.md)), and record it in `## Open` with the worker (its id and, where it asked, the question's id) in place of the head. A BLOCKED report keeps its worktree and branch ([Outcomes](outcomes.md)), and its item task gets an Orca gate once its worker settled ([Tasks and gates](orca-gates.md#tasks-and-gates)).
- After the answer the Gates section of [orca-gates.md](orca-gates.md#gates) brings it to the same worker, a supervised Claude Code worker gets it by a follow-up `send` in place, or by a new start when it is released, its terminal is gone or its terminal shows no auto mode, and a `follow_up` not confirmed in its own terminal is kept for the owner, with nothing stopped or started ([Follow-ups](orca-follow-ups.md)); an automatic worker's answer, and one whose worker failed, was stopped or is gone, goes to a new start in its worktree with the gate form of the spec's Branch line ([spec-template.md](spec-template.md), [SKILL.md](SKILL.md#loop), step 3) and the answer under `Shared context:` as a line of its own marked `(owner)` ([Owner-only decisions](decisions.md#owner-only-decisions)). Either counts like a follow-up for the caps ([SKILL.md](SKILL.md#loop), step 5). The item goes on and ends with a new report. An answer that holds, and no answer, keep it blocked: list it in the report.

### Worker rules

[worker-rules.json](worker-rules.json) is one deny list for each Claude Code worker that runs in a session of its own. Deny wins over ask and allow, across every settings scope, so a broad allow rule in the user settings does not lift it ([permissions](https://code.claude.com/docs/en/permissions#manage-permissions)). It acts in every mode, auto mode included ([permission modes](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves)). Orca's own launch starts no Claude Code worker ([orca.md](orca.md#start-the-run)). The file holds deny rules only: on entering auto mode Claude Code drops broad allow rules (`Bash(*)`, wildcarded interpreters, package-manager run commands, `Agent` and `Monitor` allow rules) while narrow ones stay in effect ([permission modes](https://code.claude.com/docs/en/permission-modes)). Without managed settings, a `managed-mcp.json` or a Team or Enterprise login, a mod can approve a call a deny rule refuses, and a PreToolUse hook can approve what `dontAsk` would deny. Mods that Claude writes do not load in `dontAsk` mode, and a mod's own tool calls raise no prompt under an ask rule or in `dontAsk`, so the Edit rules that go in as ask do not bind them; deny rules still do ([changelog](https://code.claude.com/docs/en/changelog)).

Supervised, the list's Read rules (`.env`, `.env.*`, `secrets/`) bind the file tools, the Bash file commands Claude Code recognizes (such as `cat` and `head`) and Bash redirections ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit)), and any other Bash command still reads those files (`cut -d= -f1 .env` did).

- Supervised (Orca): before each start and follow-up of a Claude Code worker, `node <skill folder>/worker-settings.mjs --supervised <worktree path> <project path>` writes the list as `<worktree path>/.claude/settings.local.json`, then the same command with `--check` before `--supervised` must exit 0. Claude Code reads that file in the folder it starts in beside the main checkout's and applies the permission rules of both ([settings](https://code.claude.com/docs/en/settings#where-claude-code-keeps-the-local-file-in-a-git-repository)). The file also sets `permissions.disableBypassPermissionsMode` to `"disable"`, which keeps anyone from entering bypass mode: Claude Code then rejects `--dangerously-skip-permissions` and ignores an agent definition's `permissionMode: bypassPermissions` ([settings reference](https://code.claude.com/docs/en/settings-reference)). It closes what the launch's `--permission-mode auto` does not: bypass in the Shift+Tab cycle, which a `defaultMode` of `"bypassPermissions"` in the user, `--settings` or managed settings puts there, and a session resumed in a settings file's mode ([Follow-ups](orca-follow-ups.md)). Where the main checkout's file sets the same key, its value applies (unverified: that the key takes effect from the worktree's file). The write refuses a rule file with any other content, a file without the key included, and the item is BLOCKED. Deny rules need no workspace trust. The script refuses a path that is no linked worktree of that project ([Sandbox on](#sandbox-on)), never overwrites another file there and never writes or reads through a link: any failure starts no worker and makes the item BLOCKED. It also lists `/.claude/settings.local.json` in the shared `.git`'s `info/exclude`, which git reads for every worktree and the main checkout, and `--check` fails without that line: `git add -A` leaves the file out, `git add -f` does not, and the spec forbids staging it ([orca.md](orca.md#start-the-run)).
- Supervised, such a worker commits and reports, and the coordinator pushes its branch and opens its draft pull request ([Commit and push](commit-and-push.md)); its spec changes as [spec-variants.md](spec-variants.md#supervised-claude-code-worker-on-orca) says. With the sandbox on in a settings file the worker loads (the user settings, the main checkout's `.claude/settings.local.json`), the sandbox takes the list's Edit denies (`.claude/`, `.github/` and any `.git`) for Bash too and closes the same paths to git ([sandboxing](https://code.claude.com/docs/en/sandboxing#permission-rules)): the worker's commit can fail, and it then reports BLOCKED.
- Automatic: `worker-settings.mjs` adds the list to the settings file ([Sandbox on](#sandbox-on)), minus a rule that the template's deny list already matches (`Bash(gh *)`, `Bash(git push *)`, `WebFetch`, `.claude`). An Edit rule goes in as ask, which `dontAsk` refuses: the sandbox closes a deny rule's paths to Bash too, and so would close the shared `.git` to git. A mod's own tool calls pass those ask rules: against them, the `.github/` check of [Commit and push](commit-and-push.md) (step 2) and its read of `<W>/.git` hold.
- A Bash rule matches the command as written: `git -C . push`, `gh api` and `/bin/rm` pass it ([permissions](https://code.claude.com/docs/en/permissions#bash-rule-limits)). A `WebFetch` rule names hosts to match, never hosts to leave out, and deny wins over allow, so the deny refuses every host, also one an allow rule lists. In auto mode a supervised worker's Bash write to its rule file goes to the classifier, and the deny rules do not bind Bash writes. A `Read` deny also refuses Edit and Write on that path, `.env.example` included, at any depth, and in automatic mode the sandbox closes it to Bash too ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit), [sandboxing](https://code.claude.com/docs/en/sandboxing#permission-rules)).

### Sandbox on

The worker's settings file is written by `node <skill folder>/worker-settings.mjs <worktree path> <project path> <run folder>/settings/<id>.json <domain>...`, the paths absolute, the domains being the policy's `sandbox.allowedDomains`, never by hand: [automatic-settings.json](automatic-settings.json) with `//W/` as the worktree, `//C/` as the real path of `<project path>/.git` and the domains as `sandbox.network.allowedDomains`. The folder the worktree's `.git` file names, resolved as git opens it (each link followed before a `..` applies), must lie directly under `<project path>/.git/worktrees`, compared by file identity, so no other spelling of a folder and no folder outside the project's `worktrees` folder passes. The worktree's `.git` file goes into `sandbox.filesystem.denyWrite`: on macOS the sandbox runtime alone blocks only creating, removing and renaming it, not a write in place. The worker cannot write the file: the file tools, the sandbox and `dontAsk` keep it to its worktree.

- Claude Code v2.1.323 or later (`'<claude path>' --version`, the executable every launch line starts), the CedarLoom minimum, also for a supervised Claude Code worker ([orca.md](orca.md#start-the-run)): an older version may ignore a key it does not know, and may start a session that asks for auto mode in a mode that allows more.
- The file tools keep to the worktree (`blockWritesOutsideWorkingDirectories`, `blockReadsOutsideWorkingDirectories`), and with the sandbox on the read block also closes the home folder and the other users' folders to Bash. Bash writes reach the worktree minus its `.git` file, the temporary folder and the shared `.git` minus `hooks`, `config` and the paths of the deny rules below, so a package manager whose cache lies in the home folder fails there (`npm ci`: `EPERM` on `~/.npm/_cacache`). The credential entries keep SSH, cloud, container and GPG credentials closed and unset the GitHub and npm tokens for every command.
- The worker reaches no Orca app: the read block closes the home folder, where Orca's runtime file lies, and the sandbox closes local sockets ([sandbox runtime README](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/README.md): "Unix sockets are **blocked by default** on both platforms", on Linux through seccomp on x64 and arm64 only), and neither is opened. The credential entries also unset `ORCA_PAIRING_CODE`, `ORCA_REMOTE_PAIRING` (the Orca CLI reads a pairing code from either) and `ORCA_AGENT_SESSION_SPAWN_TOKEN`. So it runs no Orca command and ends with its report as its final answer, which the coordinator reads through Orca ([Worker reports](orca-messages.md#worker-reports)); it never asks.
- The network allow list is `strictAllowlist` with the policy's hosts: what the project's own tools fetch. The worker neither pushes nor runs `gh`, so no GitHub host is needed for git. The `Bash(git push *)` deny stops the plain form only: `git -C . push` passed it and failed at the sandbox's network proxy, so the push bound rests on the allow list and on credentials, and a GitHub host in the allow list runs the project supervised ([Automatic start](automatic-start.md), check 4). A known residual risk: the sandbox's proxy does not inspect TLS, so code in the sandbox can reach other hosts through an allowed one ([security limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)). On macOS the credential entries cover files and environment variables, not the Keychain: the sandbox profile allows the security daemon ([sandbox runtime source](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/macos-sandbox-utils.ts)), so a sandboxed command may read a Keychain item, such as the Claude Code credentials item.
- The deny rules close the paths that configure Claude Code or run later outside the sandbox (`.claude`, `.mcp.json`, `.vscode`, `.idea`, `.bashrc`, `.zshrc`, `.gitconfig`, `.envrc`, `.npmrc`, `.husky`), and `commondir` and `config.worktree` in the shared `.git` and in each of its `worktrees/*` folders, which would make git load configuration the worker wrote: in the main checkout and in any worktree of the project, outside the sandbox. An item that must change one is BLOCKED for the owner.
- For each folder under the shared `.git`'s `worktrees` when the file is written, the script adds the two rules with that folder's name beside the `worktrees/*` pattern rules. Only a rule that names a path keeps its folder from being renamed, and so from being swapped for a copy with another `commondir` (on Linux through mount points: the sandbox makes each folder between a named path and the write root one, which the kernel refuses to rename), and on Linux the sandbox skips a pattern rule for writes. A folder made after the file was written has the pattern rules alone, until that worker's next settings file: on macOS they close its two files but not a rename of the folder, on Linux nothing. So no worktree of a project is made while an automatic worker of that project is started and not yet released:
  - An automatic worker is released as soon as its report arrives. Its staged change waits in the worktree, which stays, for [Commit and push](commit-and-push.md) to open its pull request. It counts as released only once its session has ended, which [Clean up](orca-clean-up.md) confirms.
  - Every later turn of that worker (a follow-up with review findings, a re-check, a conflict with the default branch) is a new start in the same worktree, with its settings file written again, so that file names the folders that exist then.
  - This is the regular case, also with one worker per project: the next issue of the project gets its worktree only once the worker before it is released, and a follow-up never runs under a settings file older than a worktree.
  - Workers that start together get their worktrees before the first of their settings files. A worktree needed while one of them still works waits until that worker is released.
  - Some automatic workers are never released or not released yet: a worker whose terminal a person typed in is never released, a start held at a dialog has loaded its settings file and so counts as started, and a worker whose session end [Clean up](orca-clean-up.md) cannot confirm stays unreleased. While one of these lasts, no worktree is made in its project, and the project's waiting issues are listed for the owner in the report and do not hold the run open.

  The `commondir` read of [Commit and push](commit-and-push.md) is the second check: the sandbox's part of this is not tested.
- Lists of rules and folders merge across every settings scope the worker loads, so the bounds are the template and the [Worker rules](#worker-rules) plus the user's and the main checkout's entries.
