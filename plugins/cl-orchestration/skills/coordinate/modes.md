# Worker modes

The two modes, their gates, the rule file of a Claude Code worker and the bounds of an automatic one: [Modes](#modes), [Gates](#gates), [Worker rules](#worker-rules), [Automatic bounds](#automatic-bounds). The checks before an automatic worker starts are in [automatic-start.md](automatic-start.md), the coordinator's commit and push of a worker's change in [commit-and-push.md](commit-and-push.md).

## Modes

Each project's `mode` comes from its policy ([policy.md](policy.md)). A leading `--mode supervised` run argument lowers every project of the run to supervised; nothing raises a mode. The handoff's `Mode:` line holds each project's mode for the run and, where lower than its policy's, why; a resumed run keeps it.

- **Supervised:** a Claude Code worker starts in auto mode (`--permission-mode auto`, Manual where auto mode is unavailable) in a terminal the coordinator makes, with the rule file of [Worker rules](#worker-rules); another agent's worker starts through Orca's own launch, so its prompts depend on Orca's agent permission setting, the user's choice ([orca.md](orca.md#start-the-run)). The coordinator writes no flag that bypasses or skips permission prompts; a worker's prompts are the owner's ([A permission dialog](orca-watch.md#a-permission-dialog)).
- **Automatic:** a Claude Code worker starts only with its settings file (below), with `--permission-mode dontAsk` and `--settings <run folder>/settings/<id>.json` on its launch, the absolute path that the `--check` read of [Automatic start](automatic-start.md) took; a call the allow rules do not cover, or a deny rule refuses, is denied, never prompted. No flag that bypasses permission prompts, in any form, and its settings file sets `disableBypassPermissionsMode` to `"disable"` ([settings](https://code.claude.com/docs/en/settings)), so a hook cannot switch the session to bypass mode either ([changelog](https://code.claude.com/docs/en/changelog)). A worker takes one issue, whatever `issuesPerWorker` says: it cannot commit, so it cannot switch branches. Its spec changes as [spec-variants.md](spec-variants.md#automatic-mode) says.

`dontAsk` only refuses tool calls that no allow rule lists; it decides no question: an owner-only decision is a gate ([Gates](#gates)).

### Gates

A gate holds one item for the owner while the other items go on ([Owner-only decisions](decisions.md#owner-only-decisions)): in supervised mode every question put to the owner, in automatic mode an owner-only decision only.

- Worker side: the worker never decides an owner-only question and never takes a default for it, also where a tool call would pass. With a question command and in supervised mode it asks and waits for the answer; otherwise it stops that item and reports BLOCKED with the question ([spec-template.md](spec-template.md)).
- Coordinator side: put each such question to the owner once, in your own words, as an approval whose What starts with `question` and names the issue and the decision ([approvals.md](approvals.md)), and record it in `## Open` with the worker (its id and, where it asked, the question's id) in place of the head. A BLOCKED report keeps its worktree and branch ([Outcomes](outcomes.md)), and its item task gets an Orca gate once its worker settled ([Tasks and gates](orca-gates.md#tasks-and-gates)).
- After the answer the Gates section of [orca-gates.md](orca-gates.md#gates) brings it to the same worker, a supervised Claude Code worker gets it by a follow-up `send` in place, or by a new start when it is released, its terminal is gone or its terminal shows no auto mode, and a `follow_up` not confirmed in its own terminal is kept for the owner, with nothing stopped or started ([Follow-ups](orca-follow-ups.md)); an automatic worker's answer, and one whose worker failed, was stopped or is gone, goes to a new start in its worktree with the gate form of the spec's Branch line ([spec-template.md](spec-template.md), [SKILL.md](SKILL.md#loop), step 3) and the answer under `Shared context:` as a line of its own marked `(owner)` ([Owner-only decisions](decisions.md#owner-only-decisions)). Either counts like a follow-up for the caps ([SKILL.md](SKILL.md#loop), step 5). The item goes on and ends with a new report. An answer that holds, and no answer, keep it blocked: list it in the report.

### Worker rules

[worker-rules.json](worker-rules.json) is one deny list for each Claude Code worker that runs in a session of its own. Deny wins over ask and allow, across every settings scope, so a broad allow rule in the user settings does not lift it ([permissions](https://code.claude.com/docs/en/permissions#manage-permissions)). It acts in every mode, auto mode included ([permission modes](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves)). Orca's own launch starts no Claude Code worker ([orca.md](orca.md#start-the-run)). The file holds deny rules only: on entering auto mode Claude Code drops broad allow rules (`Bash(*)`, wildcarded interpreters, package-manager run commands, `Agent` and `Monitor` allow rules) while narrow ones stay in effect ([permission modes](https://code.claude.com/docs/en/permission-modes)). Without managed settings, a `managed-mcp.json` or a Team or Enterprise login, a mod can approve a call a deny rule refuses, and a PreToolUse hook can approve what `dontAsk` would deny. Mods that Claude writes do not load in `dontAsk` mode, and a mod's own tool calls raise no prompt under an ask rule or in `dontAsk`, so an ask rule does not bind them; deny rules do ([changelog](https://code.claude.com/docs/en/changelog)).

Supervised, the list's Read rules (`.env`, `.env.*`, `secrets/`) bind the file tools, the Bash file commands Claude Code recognizes (such as `cat` and `head`) and Bash redirections ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit)), and any other Bash command still reads those files (`cut -d= -f1 .env` did).

- Supervised (Orca): before each start and follow-up of a Claude Code worker, `node <skill folder>/worker-settings.mjs --supervised <worktree path> <project path>` writes the list as `<worktree path>/.claude/settings.local.json`, then the same command with `--check` before `--supervised` must exit 0. Claude Code reads that file in the folder it starts in beside the main checkout's and applies the permission rules of both ([settings](https://code.claude.com/docs/en/settings#where-claude-code-keeps-the-local-file-in-a-git-repository)). The file also sets `permissions.disableBypassPermissionsMode` to `"disable"`, which keeps anyone from entering bypass mode: Claude Code then rejects `--dangerously-skip-permissions` and ignores an agent definition's `permissionMode: bypassPermissions` ([settings reference](https://code.claude.com/docs/en/settings-reference)). It closes what the launch's `--permission-mode auto` does not: bypass in the Shift+Tab cycle, which a `defaultMode` of `"bypassPermissions"` in the user, `--settings` or managed settings puts there, and a session resumed in a settings file's mode ([Follow-ups](orca-follow-ups.md)). Where the main checkout's file sets the same key, its value applies (unverified: that the key takes effect from the worktree's file). The write refuses a rule file with any other content, a file without the key included, and the item is BLOCKED. Deny rules need no workspace trust. The script refuses a path that is no linked worktree of that project ([Automatic bounds](#automatic-bounds)), never overwrites another file there and never writes or reads through a link: any failure starts no worker and makes the item BLOCKED. It also lists `/.claude/settings.local.json` in the shared `.git`'s `info/exclude`, which git reads for every worktree and the main checkout, and `--check` fails without that line: `git add -A` leaves the file out, `git add -f` does not, and the spec forbids staging it ([orca.md](orca.md#start-the-run)).
- Supervised, such a worker commits and reports, and the coordinator pushes its branch and opens its draft pull request ([Commit and push](commit-and-push.md)); its spec changes as [spec-variants.md](spec-variants.md#supervised-claude-code-worker-on-orca) says.
- Automatic: `worker-settings.mjs` adds the list to the settings file ([Automatic bounds](#automatic-bounds)), minus a rule that the template's deny list already matches (`Bash(gh *)`, `Bash(git push *)`, `WebFetch`, `.claude`). Its Edit rules bind the file tools only: Bash still writes those paths, git's own writes to `.git` included, so the `.github/` check of [Commit and push](commit-and-push.md) (step 2) and its read of `<W>/.git` hold against them.
- A Bash rule matches the command as written: `git -C . push`, `gh api` and `/bin/rm` pass it ([permissions](https://code.claude.com/docs/en/permissions#bash-rule-limits)). A `WebFetch` rule names hosts to match, never hosts to leave out, and deny wins over allow, so the deny refuses every host, also one an allow rule lists. In auto mode a supervised worker's Bash write to its rule file goes to the classifier, and the deny rules do not bind Bash writes. A `Read` deny also refuses Edit and Write on that path, `.env.example` included, at any depth ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit)).

### Automatic bounds

The worker's settings file is written by `node <skill folder>/worker-settings.mjs <worktree path> <project path> <run folder>/settings/<id>.json`, the paths absolute, never by hand: [automatic-settings.json](automatic-settings.json) with `//W/` as the worktree and `//C/` as the real path of `<project path>/.git`. The folder the worktree's `.git` file names, resolved as git opens it (each link followed before a `..` applies), must lie directly under `<project path>/.git/worktrees`, compared by file identity, so no other spelling of a folder and no folder outside the project's `worktrees` folder passes. The file lies in the run folder, outside the worktree that the file tools keep the worker to.

- Claude Code v2.1.323 or later (`'<claude path>' --version`, the executable every launch line starts), the CedarLoom minimum, also for a supervised Claude Code worker ([orca.md](orca.md#start-the-run)): an older version may ignore a key it does not know, and may start a session that asks for auto mode in a mode that allows more.
- The file tools keep to the worktree (`blockWritesOutsideWorkingDirectories`, `blockReadsOutsideWorkingDirectories`). The `Bash` allow rule runs every command no deny rule refuses, with the user's rights: the deny rules, the role guard of `cl-workflow` and the isolated environment the run works in bound those commands. Run an automatic project only in an isolated environment, a dedicated machine or VM you can restore, or a dev container, with tokens scoped to the work ([dev containers](https://code.claude.com/docs/en/devcontainer)). CedarLoom does not support the Claude Code sandbox yet.
- What a Bash command reaches (the home folder, the network, local sockets such as Orca's, the credentials of that environment) only the isolated environment bounds. The worker runs no Orca command because its spec says so ([spec-variants.md](spec-variants.md#automatic-mode)) and ends with its report as its final answer, which the coordinator reads through Orca ([Worker reports](orca-messages.md#worker-reports)); it never asks.
- The `Bash(gh *)` and `Bash(git push *)` deny rules stop the plain forms only: `git -C . push` passes them. The role guard refuses a push to the default branch or a tag; any other push rests on the environment's token and the repository's rulesets.
- The deny rules close to the file tools the paths that configure Claude Code or run later (`.claude`, `.mcp.json`, `.vscode`, `.idea`, `.bashrc`, `.zshrc`, `.gitconfig`, `.envrc`, `.npmrc`, `.husky`), and `commondir` and `config.worktree` in the shared `.git` and in each of its `worktrees/*` folders, which would make git load configuration the worker wrote. An item that must change one is BLOCKED for the owner. A Bash command can still write them: the `commondir` read of [Commit and push](commit-and-push.md) is the check that holds.
- An automatic worker is released as soon as its report arrives. Its staged change waits in the worktree, which stays, for [Commit and push](commit-and-push.md) to open its pull request. Every later turn of that worker (a follow-up with review findings, a re-check, a conflict with the default branch) is a new start in the same worktree, with its settings file written again.
- Lists of rules merge across every settings scope the worker loads, so the bounds are the template and the [Worker rules](#worker-rules) plus the user's and the main checkout's entries.
