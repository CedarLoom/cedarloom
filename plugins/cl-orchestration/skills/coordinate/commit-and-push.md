# Commit and push

How the coordinator commits, checks and pushes a worker's change and opens its draft pull request: the read of `<W>/.git`, `gitW`, steps 1 to 5, and what applies to a supervised Claude Code worker on Orca.

The worker stages its change and reports the branch, the staged files and a commit message. The worker can write the refs, replace objects and grafts of the shared `.git`, so these steps take commits from origin, never from local refs or history. It can also write the worktree's folder there, which `<W>/.git` names: before each step and any other git command of yours in `<W>` (Clean up's too), read `<W>/.git` and that folder's `commondir` with the file tool. The folder lies directly under `<project path>/.git/worktrees/`, `commondir` holds `../..`, the folder's `config.worktree` is missing or empty, and the shared `.git` has no `commondir`; anything else (git would load configuration, and so commands, the worker wrote) makes the item BLOCKED. An empty `config.worktree` is accepted: it holds no configuration. The settings file's deny rules close these to the worker's file tools, not to its Bash commands: this read is the check that holds.

Every git command of yours in `<W>`, below and in Clean up, runs as `git --no-replace-objects -C <W> -c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.ext.allow=never`, written `gitW` here: a hook (also of a fetch, which writes a ref), a monitor or an `ext::` remote would run worktree code in your session, so the project's hooks do not run here and its CI checks the change. `policy.mjs` pins the same three. `core.hooksPath` does not reach a hook that git config defines: for each `hook.<name>` that `gitW config --list` shows, in any scope, `gitW` also takes `-c hook.<name>.enabled=false`, and a name that holds `=`, which `-c` cannot turn off, makes the item BLOCKED.

1. `gitW rev-parse HEAD` is a commit of origin: `gh api repos/<owner/repo>/compare/<that sha>...<branch>` (while origin has no such branch, `<default branch>`) gives `identical` or `ahead`. In a merge round (step 5), `gitW rev-parse MERGE_HEAD` is the sha that step merged. Anything else (a worker commit) makes the item BLOCKED.
2. `gitW diff --cached --no-renames --ignore-submodules=none --name-only` (in a merge round, against `MERGE_HEAD`) lists the reported files, all in the owned paths; without `--ignore-submodules=none` a `.gitmodules` the worker wrote can hide a changed submodule commit. A `CHERRY_PICK_HEAD` that `gitW rev-parse -q --verify CHERRY_PICK_HEAD` finds makes the item BLOCKED: `git commit` would take the author of the commit it names. A path under `.github/` is the owner's (workflows, the actions and scripts they call run in CI with the repository's secrets before review): BLOCKED with the question, before the push. The project's own tests and scripts, which CI runs too, are outside this check.
3. Write the message to a file in the run folder with the file tool, then `gitW commit -F <file>`. The commit is signed where the owner's git configuration signs. Before the push, check the commit itself: `git commit` takes its tree from the index's cache and adds a `MERGE_HEAD` file as a parent, both of which the worker can write, so steps 1 and 2 do not prove what it holds.
   Right after the commit, `gitW rev-parse HEAD` once gives `<commit sha>`; the checks and the push take that sha and never resolve `HEAD` again, since the worker can move the ref in between.
   - `gitW cat-file commit <commit sha>` has exactly one `parent` line, the step 1 sha (in a merge round two: that sha, then the merged sha). Read the raw commit, never `rev-list` or `log`: a grafts file the worker wrote changes the parents they show.
   - `gitW diff --no-renames --ignore-submodules=none --name-only <step 1 sha> <commit sha>` (in a merge round, against the merged sha) prints the list step 2 accepted.

   Anything else makes the item BLOCKED, and nothing is pushed. Then `gitW push --no-follow-tags --no-recurse-submodules origin <commit sha>:refs/heads/<branch>`. First round: `gh pr create -R <owner/repo> --draft --base <default branch> --head <branch> --title "<your own words>" --body-file <file>`, the file holding the commit message and, where the policy's `closeIssue` is true and the pull request is not one of an approved pull request list, a line `Closes #<number>` for its issue ([Ready](merge.md#ready)). Run it in the run folder, never in `<W>`: `gh` reads the git config of its working folder. A new title or body the worker answers with is the coordinator's to set, a new body with the same `Closes` line.
4. Before a follow-up, `gitW fetch origin <branch>` and `gitW merge --ff-only <sha>`, the sha `gitW ls-remote origin refs/heads/<branch>` prints: `gh pr update-branch` moves the branch on origin.
5. A conflict with the default branch: the same with `<default branch>` and `merge --no-commit` in place of `--ff-only`, then the follow-up. The worker resolves and stages, and step 3's commit is the merge.

A supervised Claude Code worker on Orca commits on its branch, fetches and merges itself, and reports its branch, its head commit, a proposed pull request title and a body ([spec-variants.md](spec-variants.md#supervised-claude-code-worker-on-orca)), so steps 1, 3's commit, 4 and 5 do not apply. The `commondir` read and `gitW` above do. Such a worker runs under the host login without the automatic bounds and can write the shared `.git`, its config included: these steps catch a mistake, not a worker that works against them. The push runs hook-free as well: a hook in that `.git` is the worker's to write, so it would run the worker's code as you; the worker's own commit ran the project's commit hooks, and CI checks the change. `gitW rev-parse refs/heads/<branch>` prints the reported commit, which is `<commit sha>` from then on, and after `gitW fetch origin <default branch>`, every path that `gitW diff --no-renames --ignore-submodules=none --name-only refs/remotes/origin/<default branch>...<commit sha>` or `gitW log --format= --name-only --cc --no-renames --ignore-submodules=none --no-show-signature refs/remotes/origin/<default branch>..<commit sha>` lists is owned, by step 2's rule: the push publishes every commit, so a file one commit adds and a later one removes counts too, and with `--cc` the log also lists the files a merge's resolution changed, but not a path a merge took back to the branch's side, which only the diff lists; `--no-show-signature` keeps a `log.showSignature` setting from adding lines that read as file names. Anything else makes the item BLOCKED, and nothing is pushed. Then push and open the draft pull request as the end of step 3 says: the title in your own words, which may follow the one the worker proposed, and the worker's body written to a file in the run folder with the file tool for `--body-file`, never on the command line. A new title or body for a follow-up goes the same way through `gh pr edit <n> -R <owner/repo> --title "<your own words>" --body-file <file>`. A follow-up's new head is pushed the same way; origin refusing it as no fast-forward makes the item BLOCKED, never a forced push. A batch's worker goes on in the same worktree meanwhile: a git command that fails on a locked ref runs again at the next wake-up, and a second failure makes the item BLOCKED.
